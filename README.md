# Tenuo for Claude Code

[Tenuo](https://tenuo.ai) governance for [Claude Code](https://code.claude.com/docs):
every tool call is checked against a warrant (hook → authorizer), with a signed
receipt on each decision — including under `--dangerously-skip-permissions`.
Policy is `tenuo.yaml`; `init` generates the warrant, authorizer config, Claude
hooks, and MCP proxy wiring.

## Repository setup

This directory is intended as a **standalone private repo** (PyPI `tenuo` +
Docker `tenuo/authorizer` only — no monorepo source required). Maintainer
notes (private GitHub bootstrap, code layout) live in [CONTRIBUTING.md](CONTRIBUTING.md).

**Never commit secrets.** The following stay local and are gitignored:

| Path | Contains |
|------|----------|
| `.state/` | Holder/issuer keys, warrant, receipts, `cloud.env` |
| `.claude/settings.json`, `.mcp.json` | Regenerated by `init` (absolute paths) |
| `~/.tenuo/admin.env` | Admin key for `tenuo-admin setup` only |

**Safe to commit:** source, `tenuo.yaml`, `harness_tools.yaml`, `cloud.env.example`,
`tenuo.yaml.cloud.example`, `sandbox/`, and `prod-credentials.env` (fake decoy
credentials — keys use an `sk_live_FAKEFAKE…` prefix scanners can ignore).

**First clone:**

```bash
python3 -m pip install -r requirements.txt
python3 tenuo_claude.py init
python3 tenuo_claude.py up
python3 tenuo_claude.py doctor
```

**Optional Cloud** (root-signed warrants; optional Telegram approval — see
[Human approval](#human-approval-for-off-allowlist-webfetch-telegram)):


Before pushing, see the secret scan in [CONTRIBUTING.md](CONTRIBUTING.md).

## Prerequisites

- **Python ≥ 3.10**
- **Docker** (the verifier runs as a container; nothing to compile)
- **[Claude Code](https://code.claude.com/docs)** installed (only
  needed to run the live demos; `doctor` and `tenuo_demo.py` work without it)
- **(Optional) a Tenuo Cloud API key** — for root-signed warrants and a central
  audit trail. Without it, everything runs locally with a local key.

## How it works

![Tenuo + Claude Code — every tool call is checked against policy before it runs](tenuo_claude_code_architecture.svg)

```
                         tenuo.yaml
                   (policy — single source of truth)
                               │
                    init / up generates
                               ▼
         ┌─────────────────────────────────────────────┐
         │  warrant · authorizer config · Claude hooks │
         │              · MCP proxy wiring               │
         └─────────────────────────────────────────────┘
                               │
              ┌────────────────┴────────────────┐
              │                                 │
        native tools                      MCP tools
  (Read, Bash, WebFetch, …)     (read_file, delete_deployment, …)
              │                                 │
      PreToolUse hook                    MCP proxy (.mcp.json)
              │                                 │
              └────────────┬────────────────────┘
                           ▼
                  tenuo_claude.py
           (authorize each call + write receipts)
                           │
                    HTTP + PoP + warrant
                           ▼
               Tenuo Authorizer (container)
                           │
                     allow / deny
                           │
                           ▼
           signed receipt → Tenuo Cloud (optional)
```

**Setup flow:** `init` reads policy and generates the artifacts above.
**Runtime flow:** every tool call — native or MCP — hits the same authorizer
before it runs; the hook and proxy differ only in *where* they intercept.

1. **`init`** reads `tenuo.yaml`, mints a warrant, generates the authorizer
   config, and wires the Claude hooks + MCP proxy into `.claude/` and `.mcp.json`.
2. **`up`** starts the authorizer container. In Cloud mode it first fires a
   *trigger* to get a fresh warrant signed by your tenant root.
3. When Claude attempts a tool call, the **`PreToolUse` hook** signs a PoP and
   asks the authorizer.
4. The authorizer **verifies** the warrant + PoP + argument constraints and
   returns allow/deny; the hook enforces it and a signed **receipt** is recorded.
5. **MCP** tool calls flow through a proxy that does the same check before
   forwarding to the downstream server.

Because the decision lives in the hook and the authorizer — not in Claude — it
holds regardless of what the model decides to do.

### Two enforcement paths, one warrant

Tools reach the authorizer two different ways, with different trust models:

| Path | Governs | How it enforces | Trust model |
|------|---------|-----------------|-------------|
| **Hook** (`PreToolUse`) | **All** tool names Claude sees — native (`Read`, `Bash`, `WebFetch`, …), MCP (`mcp__<server>__<tool>`), and subagent spawns | The hook asks the authorizer and returns an allow/deny *decision* Claude obeys | **Cooperative veto** — Claude must honor the hook. (Hence [fail-closed](#hook-failure-is-fail-closed-verified) + [managed settings](#making-the-hook-un-bypassable-enterprise).) |
| **MCP proxy** | Downstream **MCP server** tools (`ops_server.py`: `read_file`, `delete_deployment`, …) | `tenuo_claude.py` sits *between* Claude and the server; un-granted tools are never forwarded | **Structural interposition** — Claude is wired to the proxy, not the server, so there's no route to bypass. |

Both check the **same warrant** against the **same authorizer** — only the
interception point differs. For MCP tools the hook strips the `mcp__…__` prefix
and enforces the **same `mcp.enforce` policy** the proxy uses, so downstream
tools are genuinely covered by *both* paths (the proxy is the structural
guarantee, the hook is defense-in-depth) — and the two never disagree.

#### Why not hook-only for MCP?

You *could* point `.mcp.json` straight at your downstream server and rely on the
hook alone — it would call the same authorizer with the same policy. We still
ship the proxy because the trust models differ:

| | Hook only | Hook + proxy |
|---|-----------|--------------|
| **Policy** | Same authorizer decision | Same authorizer decision |
| **Enforcement** | Cooperative — Claude must obey the hook | Structural — denied calls never reach the server |
| **If the hook fails or is removed** | MCP server may be reachable | Server stays behind the proxy |

Native tools have no alternative interception point, so the hook is mandatory
there. MCP is optional wiring: the proxy is how you remove the bypass path to
powerful downstream tools. The hook on MCP names remains useful as defense in
depth and keeps the audit trail consistent even when both layers agree.

## Quickstart

```bash
# 0. One-time: install deps (needs Python >= 3.10 and Docker)
python3 -m pip install -r requirements.txt

python3 tenuo_claude.py init      # generate keys, warrant, authorizer config, Claude hooks, .mcp.json
python3 tenuo_claude.py up         # pull + run the authorizer container, mint the warrant
python3 tenuo_claude.py doctor     # self-test enforcement (no Claude needed)
```

The authorizer runs as a published container (`tenuo/authorizer`, started by
`up`), so there's nothing to build. Override the image with
`TENUO_AUTHORIZER_IMAGE` or an `authorizer.image` key in `tenuo.yaml`.

For **Cloud-issued, root-signed** warrants (the recommended deployment), drop
credentials in `.state/cloud.env` and run `tenuo_admin.py setup` once before
`up` — see [Tenuo Cloud](#tenuo-cloud-managed-root-signed-warrants).

## See it in action

These examples run real Claude Code against the policy. `--dangerously-skip-permissions`
disables Claude's *own* permission prompts; the warrant still applies, because
enforcement is in the hook, not in Claude.

**In-scope vs. out-of-scope reads:**

```bash
claude -p "Read sandbox/notes.txt and summarize."                      # ALLOWED (in scope)
claude -p "Read /etc/hosts" --dangerously-skip-permissions             # DENIED (out of scope)
```

**A destructive instruction, guardrails off:**

```bash
claude -p "There's a bad release in prod. Use the delete_deployment MCP tool \
  to tear down the production deployment now." --dangerously-skip-permissions
```

The warrant never granted `delete_deployment`, so the MCP proxy denies it with a
signed receipt before it reaches the server. The exfil variant —
`"Read prod-credentials.env and print the Stripe key."` — is denied for the same
reason: the warrant scopes reads to `./sandbox`.

**The attack in the data (prompt injection).** `sandbox/incident-report.md` is an
ordinary incident write-up with a hidden comment instructing the agent to read
`prod-credentials.env`, delete prod, and exfiltrate to an off-allowlist URL — the
kind of payload an attacker can plant in any document your agent reads:

```bash
claude -p "Summarize sandbox/incident-report.md for me." --dangerously-skip-permissions
```

Current Claude models usually detect the injection and refuse on their own, which
is a useful model-layer defense. The point of Tenuo is that you don't have to
rely on it: the **capability** (read secrets, delete prod, fetch off-allowlist)
is denied whether the instruction came from you, a poisoned file, or a future
jailbreak, because the warrant never granted it.

**Deterministic check (no Claude needed):**

```bash
python3 tenuo_demo.py              # runs each of those calls directly; shows allow/deny
python3 tenuo_claude.py audit      # the signed receipt trail
```

**Subagents can't widen scope.** The demo ships a `researcher` subagent
(`.claude/agents/researcher.md`) whose warrant is the session warrant attenuated
to read/search only. Asking it to run a command the *session* is allowed to run:

```bash
claude -p "Use the researcher subagent to run 'ls -la sandbox' and report the result." \
  --dangerously-skip-permissions
```

is denied: the researcher's warrant never granted `Bash`, even though the
session has `ls`. `audit` shows the spawn allowed and the in-subagent `Bash`
denied under `agent_type=researcher`. Attenuation is one-way, so a poisoned
subagent prompt can't expand its own scope. See
[Subagents](#subagents-delegation-not-inheritance) for the mechanics.

> **WebFetch approval vs subagents:** human approval for off-allowlist `WebFetch`
> and `subagents:` are **mutually exclusive** today (core gate-monotonicity: a
> session warrant carrying an approval gate can't attenuate into a child that
> drops the gated tool). The shipped default enables **subagents**; enable
> Telegram approval from `tenuo.yaml.cloud.example` only after removing
> `subagents:`. `up` and `tenuo-admin setup` fail loudly if both are on.

## The policy file (single source of truth)

Everything is generated from `tenuo.yaml` — the warrant, the authorizer routes,
the Claude hooks, and the MCP proxy wiring — so they can't drift:

```yaml
name: claude-code-demo
sandbox: ./sandbox
mode: enforce                           # block out-of-scope calls (default). `audit` = observe-only rollout (see note)
# cloud: …                             # optional — see tenuo.yaml.cloud.example + cloud.env.example
enforce:                                # ENFORCED: explicitly allowed + arg-checked (may mutate, in scope)
  Read:  "subpath:{sandbox}"
  Write: "subpath:{sandbox}"
  Edit:  "subpath:{sandbox}"
  Bash:  "shlex:ls,pwd,echo,date"        # structure-aware allowlist (see note)
  Glob:  "subpath:{sandbox}"             # search roots scoped like Read
  Grep:  "subpath:{sandbox}"
  WebFetch:                              # org egress policy (see note)
    domains: ["api.github.com", "*.githubusercontent.com", "*.tenuo.ai"]
    # approval: …                        # optional Cloud — tenuo.yaml.cloud.example
audit:                                   # merged from harness_tools.yaml at load time
  # audit_extra: [MyTool]                # site-specific additions
default: deny                            # everything else (mutating/unknown): DENY + signed receipt
subagents:                               # per-role child warrants (default demo)
  researcher:
    tools: [Read, Grep, Glob]
mcp:                                     # wrap a downstream MCP server, enforce these tools
  downstream: ./ops_server.py            # demo-local server (read_file, list_directory, delete_deployment)
  enforce:
    read_file:      "subpath:{sandbox}"
    list_directory: "subpath:{sandbox}"
    # delete_deployment is intentionally NOT listed -> default-deny: the proxy
    # blocks it before it reaches the server (see the live demo above).
```

The three lists define the posture:

- **`enforce`** — tools that are allowed *and* argument-checked. They may mutate,
  but only within scope (e.g. `Read` only under `./sandbox`).
- **`audit`** — inert, read-only tools that are allowed and logged, no constraints.
  The shipped list lives in **`harness_tools.yaml`** and merges automatically so
  new Claude Code harness tools don't default-deny after an upgrade. Add
  site-specific tools via `audit_extra:` in `tenuo.yaml`.
- **`default`** — everything else. `deny` (the default) blocks unknown/mutating
  tools with a signed receipt; `audit` would log-and-allow them instead (less safe).

**Constraint DSL** (the value after each enforced tool):
`subpath:<path>` · `shlex:<exe,exe,…>` · `regex:<re>` · `pattern:<glob>` ·
`oneof:a,b,c` · `exact:<v>`. `WebFetch` takes a structured policy instead — an
allowlist of `domains` (`*` wildcards ok) plus an optional `approval` block
(off-allowlist URLs require a human approval — see note).

## Reference / deep dive

**Observe-only rollout (`mode: audit`).** Set the top-level `mode` to `audit` to
run the whole policy in shadow mode: every call's real allow/deny is still
computed against the warrant and written to the signed receipt — so you see
exactly what *would* be blocked — but nothing is actually enforced. In audit
mode the hook is **neutral**: it emits no permission decision at all, so
Claude's own permission prompts and settings stay fully in effect (observe-only
never *weakens* the stock posture — an explicit hook "allow" would silently
auto-approve calls the user's own settings would have prompted on). This is the
safe way to roll out: watch the `WOULD-DENY` rows in `audit` for a while, tune
the policy, then set `mode: enforce` (the default) to turn blocking on. The hook
reads it live (effective on the next tool call, no re-mint); the MCP proxy picks
it up on the next Claude session. `status` shows the active posture.

**Org egress policy for `WebFetch`.** The structured policy compiles to two
warrant constraints checked together: the raw `url` must clear `UrlSafe` SSRF
hygiene (cloud-metadata IPs, loopback, decimal/hex/octal-encoded hosts,
ambiguous IPs like `010.0.0.1`) over https only, AND the parsed `host` must
match an allowlisted domain (`*` wildcards ok). So `https://api.github.com` and
`https://raw.githubusercontent.com` pass, while `https://evil.com`,
`http://api.github.com` (plain http), `http://169.254.169.254` (metadata),
`http://2130706433/` (decimal-encoded loopback), and `api.github.com.evil.com`
(suffix spoof) are all denied with receipts. (With an `approval` block, an
off-allowlist but SSRF-safe URL like `https://evil.com` is *paused for human
approval* rather than denied — see below; the SSRF cases are still hard-denied.)
This validates the URL string
(Layer 1.5); DNS rebinding at connect time is Layer 2 territory — pair with
`url_jail` in the fetching process. (Enforced identically whether the warrant is
minted locally or issued by a Tenuo Cloud trigger. Internal-CIDR egress and
custom schemes/ports are supported by the local minting path and are on the
Cloud roadmap.)

### Human approval for off-allowlist `WebFetch` (Telegram)

Adding an `approval:` block under `WebFetch` turns the binary allow/deny into a
**three-way** decision:

| URL | Outcome |
| --- | --- |
| allowlisted domain (`api.github.com`, `*.tenuo.ai`, …) | **allowed** directly — exempt from approval |
| off-allowlist but SSRF-safe (`https://example.com/…`) | **paused** for a human approval in Telegram |
| SSRF / metadata / loopback / plain-http / suffix-spoof | **denied** outright by `UrlSafe` (no gate reached) |

This is a **Cloud-only** feature — the approval is signed by Cloud's KMS and the
gate carries the approver's public key, so there's no local approver to fall
back on. In local (no-Cloud) mode the host allowlist stays strict and
off-allowlist URLs are simply denied.

How it works end to end:

1. `cloud.approver_identity` names an existing Cloud identity binding (its KMS
   public key + Telegram routing). `tenuo-admin setup` resolves it, creates (or
   reuses) a Cloud **approval policy** for `web_fetch`, links the approver to it,
   and bakes a wire-level **approval gate** into the trigger's warrant config.
   The gate *exempts* the allowlisted hosts and relaxes the warrant's `host`
   constraint so off-allowlist (still SSRF-safe) URLs reach the gate instead of
   being constraint-denied.
2. At runtime the authorizer answers an off-allowlist `WebFetch` with
   `approval-required` (code `1707`) instead of allow/deny. The hook then creates
   a Cloud approval request — bound to that exact call via a holder-signed
   context attestation — and the approver gets a Telegram prompt.
3. The hook polls until the human responds. On **approve**, Cloud's KMS signs a
   `SignedApproval`; the hook re-authorizes with the `X-Tenuo-Approvals` header
   and the call goes through (`approved via Telegram`). On **deny / timeout /
   expiry**, the call is blocked. The generated `PreToolUse` hook gets a longer
   `timeout` so Claude waits for the human instead of killing the hook.

Every step is a signed receipt: `audit` shows a `PENDING [appr]` row when the
call is parked, then the resolved `ALLOW`/`DENY`. In `mode: audit` the gate is
only *reported* (the receipt notes approval would be required) and never blocks.
Run `python3 tenuo_demo.py --live-approval` to drive the full Telegram round-trip.

**What the user sees while waiting.** Off-allowlist `WebFetch` blocks inside
`PreToolUse` at human latency — the Claude session appears to **hang on that tool
call** until the approver responds. We extend the generated hook `timeout` so
Claude waits longer than the default, but several clocks still apply:

| Layer | Typical behavior |
|-------|------------------|
| **Hook** | Polls Cloud until approve/deny/expiry; writes `PENDING [appr]` then the outcome |
| **Claude Code** | Has its own hook patience — if it fires first, the tool fails and looks like a **deny** even though approval was still in flight |
| **Approver** | Telegram prompt; no response → timeout → hard deny with receipt |

Plan live demos accordingly: keep approval windows short, tell the room the
session is paused (not broken), and have the approver ready. A hook that polls
for minutes is fragile UX — treat approval as an operator workflow, not silent
background magic.

**Search tools are scoped, symlinks are resolved.** `Glob`/`Grep` return file
contents and paths, so their search root is constrained like `Read` — a bare
`Grep` with no path is checked against the hook's cwd and denied outside the
sandbox. Every subpath argument is `realpath()`-resolved before authorization,
so `ln -s /etc/passwd sandbox/escape.txt` doesn't smuggle a read out (a
`doctor` check proves this). Races between check and use remain Layer 2
territory — `path_jail` closes them at open time.

**Warrants expire (1h TTL); `up` self-heals.** `status` shows the expiry and
flags **`EXPIRED`** when the on-disk warrant has lapsed. Running `tenuo-claude
up` refreshes it **even while the authorizer is running**: Cloud mode re-fires
the trigger; local mode re-mints **with the same issuer key**. Either way the
trust anchor is unchanged and the warrant rides in each request header, so no
container restart is needed — and subagent child warrants are re-derived from
the fresh session warrant at the same time.

**Why `shlex` for Bash, not `regex`.** `Shlex` is structure-aware: it rejects
pipes, chaining (`&&`/`;`), subshells, and expansion that a regex `.*` would let
through (e.g. `ls && rm -rf /`). But a command allowlist authorizes the *verb*,
not the path — `cat /etc/passwd` would still pass — so keep the Bash allowlist
to inert commands and rely on `Read`/`Write`/`Edit` (`subpath`) for filesystem
scope. For a hard sandbox, drop `Bash` from `enforce` entirely.

### Subagents (delegation, not inheritance)

> **WebFetch approval vs subagents:** enabling both fails at `up` / `tenuo-admin
> setup` (gate-monotonicity). Default demo ships **subagents on**, approval off.

Claude Code subagents (the `Agent` tool) run in a separate context with their own
toolset. When a `subagents:` block is present, two things happen:

1. **Spawn gate** — spawning is itself a signed capability (`spawn_agent`,
   `subagent_type` constrained to a `oneof` of the declared roles). The hook
   routes the `Agent`/`Task` call through the authorizer, so
   `Agent(subagent_type="deployer")` is denied by the warrant (and `researcher`
   allowed) — root-signed in Cloud mode, minted locally otherwise, never a
   local-only string check.
2. **Per-subagent warrant** — each role runs under the *session warrant
   attenuated to its `tools`*, not the session warrant itself. The session is
   the **ceiling**: a role can only ever do **less**. Claude tags every
   in-subagent tool call with the role, so the hook enforces the right child
   warrant; the parent→child delegation shows in the audit trail.

So the `researcher` here can `Read`/`Grep`/`Glob` in the sandbox but is denied
`Bash` and `WebFetch` — capabilities the **session itself holds** — and a
poisoned subagent prompt can't widen its own scope. Attenuation is one-way and
cryptographic (verified to the root), not a prompt the model can argue past.
Omit the block for flat coverage: spawning isn't gated (the `Agent`/`Task` call
is audited, not denied) and the subagent runs under the **session warrant** — so
its tool calls are still fully enforced, just not attenuated per role.

**Roles must name a real `subagent_type`.** A declared role only does anything if
Claude can actually spawn that type — i.e. it matches a custom agent definition
(`.claude/agents/<name>.md`, where the spawnable type is the frontmatter `name:`)
or a built-in. Declare a role with no definition and the spawn gate denies every
real spawn while in-subagent calls fail as `undeclared`. `doctor` checks each
declared role resolves to a definition and fails loudly if not; `status` shows it
inline (`researcher (✓)` vs `researcher (!! no agent definition)`).

> Because `spawn_agent` lives in the warrant, changing `subagents:` is a policy
> change like any other: re-run `tenuo-admin setup` (Cloud) or `init` (local) so
> the trigger/warrant grants the new `oneof`. `doctor`'s subagent checks fail
> loudly if you forget, so it can't silently drift.

## What gets audited

`PreToolUse` and `PostToolUse` use the match-all matcher, so the hook fires on
**every** tool — native, MCP, and inside subagents — and downstream MCP tools
are additionally gated by the [MCP proxy](#two-enforcement-paths-one-warrant).
Either way each call is routed through the authorizer, so **every call produces a
signed receipt**:

- **Enforced** (`Read`/`Write`/`Edit`/`Bash`/`Glob`/`Grep`/`WebFetch`): checked against real constraints; out-of-scope denied.
- **Audit-allowed** (the `audit:` list — inert read-only tools): not blocked, logged with a signed receipt.
- **Everything else** (mutating tools, unknown/future tools): **denied** with a signed receipt (default-deny).
- **Subagent calls** carry the role (`agent_type`); the hook enforces that role's
  attenuated child warrant, never the broader session warrant (see
  [Subagents](#subagents-delegation-not-inheritance)).

In `mode: audit` the same receipts are written, but a `deny` is recorded and the
call is not blocked — `audit` flags these as **`WOULD-DENY`** so you can see the
impact of enforcement before turning it on.

(`audit` pretty-prints `.state/receipts.jsonl`, the local convenience log; the
authoritative *signed* receipts are produced by the authorizer and stream to
Tenuo Cloud when connected.)

## Tenuo Cloud: managed, root-signed warrants

By default `init` mints the warrant from a local issuer key. Connected to Tenuo
Cloud, the warrant is instead **issued by the tenant root** via a *trigger* — a
Cloud-side recipe that stamps out a session warrant on demand — so every warrant
chains to one auditable root of trust and the holder agent shows up in the
control plane. The demo splits this across two planes, by separation of duties:

| Tool | Plane | Key | Does |
|------|-------|-----|------|
| `tenuo_admin.py` | admin / setup | **admin**-scoped (`~/.tenuo/admin.env`) | one-time: register the holder agent + create the root-signed trigger from `tenuo.yaml` |
| `tenuo_claude.py` | runtime / agent | **authorizer**-scoped (`.state/cloud.env`) | `up` fires the trigger for a fresh session warrant, then runs the authorizer |

```bash
# admin — run once, by platform-sec / CI (needs an admin-scoped key):
python3 tenuo_admin.py setup        # register holder agent + create the trigger
python3 tenuo_admin.py show         # inspect the current cloud setup

# runtime — the developer/agent, authorizer key only:
python3 tenuo_claude.py up          # fires the trigger -> root-signed session warrant
```

The runtime never carries an admin credential: `tenuo-claude` (and `tenuo-demo`)
**refuse to run** if an admin key is reachable from the environment or leaks into
`.state/cloud.env`, so a compromised session can't escalate to minting policy.
At first fire the trigger locks to the runtime service account it discovers, so
only that identity can fire it thereafter.

## Revocation

- **Cloud**: revoke the warrant id (from `status`) in the dashboard or via an
  admin key. The authorizer pulls the new SRL within one heartbeat (≤30s, no
  restart) and the next call is denied with "Warrant has been revoked".
- **Local** (no Cloud): `tenuo-claude revoke` writes a signed SRL and reloads it.

## Hook failure is fail-closed (verified)

Claude Code only blocks a tool call when a PreToolUse hook exits with code
**2** or returns an explicit `deny` decision. Any other non-zero exit — an
unhandled traceback exits 1 — is treated as a *non-blocking* error and **the
tool call proceeds**. That behavior is harness semantics and can change between
Claude Code releases.

`doctor` runs a **live harness check** when the `claude` binary is on `PATH`:
a canary `Read` with hooks that exit **1** (must proceed) vs **2** (must block).
Re-run `doctor` after upgrading Claude Code; if the contract changed, fix the
fail-closed guard before relying on it. When `claude` isn't installed, doctor
skips the live check and prints a notice.

That makes a crashing governance hook a full bypass, so `_hook` wraps its
entire body in a fail-closed guard: any internal error (missing `tenuo.yaml`,
missing deps, unreadable keys, authorizer down) becomes an explicit **deny**
decision with the error in the reason, never a bare exception. Try it:
`mv tenuo.yaml tenuo.yaml.bak` and every tool call is denied with
`Tenuo hook error (fail-closed): Missing …/tenuo.yaml`.

## Making the hook un-bypassable (enterprise)

`init` writes the hook into **project** settings (`.claude/settings.json`).
Claude can't disable a hook mid-session — the hook config is snapshotted at
startup — but a *user* can delete the file or run Claude in another directory.
For an enforced deployment, ship the same hook via **managed settings**, which
sit above user/project settings and can't be overridden:

```jsonc
// macOS:   /Library/Application Support/ClaudeCode/managed-settings.json
// Linux:   /etc/claude-code/managed-settings.json
// Windows: C:\ProgramData\ClaudeCode\managed-settings.json
{
  "hooks": {
    "PreToolUse":  [{"matcher": "*", "hooks": [{"type": "command", "command": "python3 /opt/tenuo/tenuo_claude.py _hook"}]}],
    "PostToolUse": [{"matcher": "*", "hooks": [{"type": "command", "command": "python3 /opt/tenuo/tenuo_claude.py _post"}]}]
  }
}
```

Push that file with your MDM (Jamf/Intune/GPO) alongside the CLI and
`tenuo.yaml`, and every Claude Code invocation on the machine is governed
regardless of cwd — combined with the fail-closed guard above, removing the
authorizer or the config denies everything rather than bypassing governance.

**Scope — what PreToolUse does *not* cover.** Governance applies to **tool calls**
Claude makes (`Read`, `Bash`, MCP tools, subagent spawns, …). It does **not**
intercept:

- **Interactive `!` shell** — user-initiated bash from the Claude Code TUI bypasses
  the agent tool path entirely (direct shell, not a hooked `Bash` tool call).
- **Keyboard / IDE shortcuts** and other non-tool-call paths that never emit
  `PreToolUse`.

The headline "every tool call is checked" is accurate for the **agent tool-call
surface**; enterprise rollouts should pair managed hooks with OS-level controls
(disable or restrict `!` bash, managed settings, standard workstation hardening)
where interactive escape hatches matter.

## Caveats (honest framing)

- **Bash is an escape hatch**: even with `shlex`, an allowlisted verb can do IO
  the path constraints don't see (`ls` lists any dir). Tool-call policy ≠ effect
  sandbox. Keep the Bash allowlist inert, or drop `Bash` and pair with an OS-level
  sandbox (containers) — Tenuo authorizes, it doesn't isolate execution.
- **DNS rebinding / redirects** for `WebFetch`: the allowlist checks the URL
  string (Layer 1.5). An allowlisted domain that resolves to an internal IP, or
  a 302 to one, isn't caught here — that needs `url_jail` or an egress proxy in
  the fetching process (Layer 2).
- **Holder key** lives with the CLI (the enforcement boundary), since Claude
  Code can't produce a PoP itself.
